# Witness Material constitutional-write boundary investigation 001

## Question

What existing positive boundary permits material produced outside one exact
Seed physiology to enter a recorded constitutional occurrence?

This report uses **write capability**, **positive boundary**, and **whitelist**
only as repository investigation language. None names a recovered Book kind,
Responsibility, Act, relation, or Standing coordinate.

The rejected alternative is an expanding refusal list:

```text
regex
split
prefix test
parser
external process
LLM classification
...
```

Any such list can be bypassed by another mechanically equivalent operation.
The constitutional question is not which implementation operation produced
material. It is whether an exact responsible crossing admits that material to
one exact recorded occurrence.

## Existing positive sirens

Current runtime Fidelity tests establish these bounded correspondences:

```text
every live runtime event kind
-> one declared Witness Grammar Responsibility
-> one exact Book clause

every event material carrying Standing
-> a declared grammar Responsibility for that event kind

every relation-shaped runtime record
-> an admitted relation witness
```

These sirens constrain recorded species and carried coordinates. They do not
establish which caller can record an occurrence, whether its subject satisfied
the clause, or whether the recorded occurrence has positive Standing.

One narrower siren establishes that `AddressedOperatorCommand` carries no
ledger field. That exact external command-handler boundary therefore receives
no direct ledger reference through that dataclass. The finding does not cover
every Witness Material producer or every path to a recorder.

## Witness Material exclusion is not runtime exclusion

`scripts/implementation_function_measurement.py` distinguishes test functions
listed under `WITNESS_MATERIAL_TESTS` from functions measured under a Fidelity
subject. For an exact Witness Material test, `_pytest_subject()` returns no
Fidelity subject coordinates.

That establishes only:

```text
test occurrence listed as Witness Material
!= Fidelity uptake by this pytest measurement road
```

The test function still executes as ordinary Python. Nothing in that
collection distinction prevents it from importing a recorder, constructing a
ledger, or invoking a runtime function that records occurrences.

Therefore:

```text
no Fidelity measurement
!= no constitutional write path
```

## Current ledger boundary

Both `EventLedger.append()` and `SQLiteEventLedger.append()` accept:

```text
kind
material
exact_material
locality_identity
```

and record an Event. The ledger validates storage and identity boundaries. Its
public append boundary does not receive an exact Responsibility assignment,
Applicability occurrence, Participation occurrence, Act occurrence, or
Evidence-of-Yield relation as an independent authority to record.

Existing family-local recorders often reconstruct and validate those
coordinates before calling `append()`. That is valuable exact testimony. The
ledger boundary itself does not distinguish such a recorder from arbitrary
Python holding the ledger.

The current event-kind map establishes:

```text
recorded kind K
-> declared Responsibility and Book clause
```

It does not establish:

```text
caller selected K lawfully
subject satisfies that Responsibility
recording occurrence = represented occurrence
recording occurrence has Standing
```

## The missing positive boundary

The desired repository property is not:

```text
all implementation mechanisms except an approved list are forbidden
```

It is:

```text
Witness Material M
+ exact responsible boundary
+ exact subject
+ exact Applicability / Admission where required
+ exact Participation
+ exact Act occurrence
+ exact occurrence Evidence
+ exact result relation
-> one exact recorder path
-> one recorded occurrence
```

Every coordinate must be replay-validated by the family that records the
occurrence. Absence of that positive path leaves the material outside the
constitutional record regardless of whether it was produced by regex, byte
iteration, AST traversal, an external process, or an LLM.

Positive recording still establishes no positive Standing by identity. The
separate result-Standing vacancy remains.


stand in for the exact Responsibility and occurrence physiology.

Likewise, a token handed to selected Python functions would merely rename the
same list unless a recovered responsible occurrence produced, bounded, and
validated that token.
